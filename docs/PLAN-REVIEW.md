## Findings

Gaps in the plan: a scenario no criterion covers, a criterion QA cannot check, an epic too big for one PR, a risky assumption nothing covers.

| # | Finding | Severity | Closed by (epic, ADR) or accepted risk |
| --- | --- | --- | --- |
| 1 | Scenario «Ежечасное напоминание о движении»: nothing says when a «каждые N минут» reminder fires again if it is neither closed nor snoozed. The scheduler rules in SPEC Architecture and E1-AC3 restart the count only after start, after «Закрыть» and after a pause ends, yet a reply is often impossible: R-1 leaves no buttons in the Action Center, under Do Not Disturb the notification goes there without a banner (spike, 1 of 1), and a banner can time out or be swiped away. Read literally, the hourly reminder stops after the first unanswered one, and no test or QA step would show it | blocking | E1-AC7 repeats an unanswered reminder every 10 minutes with its count stopped, as SPEC Architecture now rules; E2-AC9 has QA leave one unanswered and see it again, replaced rather than doubled |
| 2 | ADR-0002 left to the A-1 spike how the AppUserModelID is registered (on the Start menu shortcut by NSIS, or by app code) and promises that the uninstaller removes the notification registration. docs/spikes/toast-buttons.md does not record what the prototype did, and no criterion requires the registration or its removal: E0-AC7 asks only for a shortcut, E2-AC7 only for the autostart key | should fix | E2-AC10 names the HKCU AppUserModelId key the prototype wrote, as SPEC Architecture records, and has the uninstaller delete it |
| 3 | E0-AC6 and SPEC Architecture give MoveReminder.App the target net10.0-windows, but Windows.UI.Notifications is reachable from .NET only with a versioned target such as net10.0-windows10.0.19041.0. That target also puts the Windows SDK projection (Microsoft.Windows.SDK.NET.dll, WinRT.Runtime.dll) into the self-contained installer, and the Dependency licences line of SPEC, which lists only .NET, Windows Forms and NSIS, leaves it out | should fix | E0-AC6 names net10.0-windows10.0.19041.0, the target of the prototype; SPEC Non-functional requirements lists both projection assemblies with their licences |
| 4 | A-4 and the 50 MB threshold of ADR-0003, a one-way decision taken with no measurement, are first measured in E3-AC7, the last epic, after E1 and E2 are built on the stack; a miss there leaves no cheap way back | should fix | E0-AC8 measures the installed tray skeleton for an hour against 50 MB and records the baseline in docs/JOURNAL.md |
| 5 | SPEC Performance targets promise a reminder no later than one minute after its due time, but no criterion checks it: E2-AC1 and E2-AC4 say only that the notification comes, and E1 tests run on fake time | should fix | E2-AC1 and E2-AC4 now require the notification no later than one minute after its due time |
| 6 | Updates are not planned. With autostart the app runs in the tray all day, so every new version installs over a running one with its files locked. A-5 names this check (install the next version over the old one: it starts by itself, settings in place), but no criterion covers it, nor says that a user who turned autostart off keeps it off after an update, while E2-AC7 turns it on at first run | should fix | E3-AC8 installs over a running app, closing it or asking to, and keeps settings.json and an autostart the user turned off; E2-AC7 enables autostart only when settings.json does not exist yet |
| 7 | E0-AC7 asks the uninstaller to remove the app, but not to remove only what the installer put there. An NSIS uninstaller that deletes the install folder recursively also deletes the user's files when the user chose an existing folder, a data deletion the normal risk class of E0 does not expect | should fix | E0-AC7 installs into the fixed folder under %LOCALAPPDATA%\Programs with no folder choice, and the uninstaller deletes only the files it installed |
| 8 | ADR-0002 decides that the installer is built on a GitHub Actions Windows runner and published to GitHub Releases, with the local build as lite staging; E0-AC4 makes the local build the release and E0-AC2 runs only the gate in CI, so no epic builds the installer on the runner | should fix | E0-AC2 has CI on windows-latest also run scripts/build and keep the installer as a workflow artifact |
| 9 | The tray menu in SPEC Architecture (Отложить, Пауза на час, Пауза до конца дня, Снять паузу, Настройки, Выход) lacks the «Автозапуск» item that E2-AC3 and E2-AC7 add | should fix | E2-AC3 and the menu in SPEC Architecture now list the same items, «Автозапуск» included |
| 10 | Saving settings.json is not required to survive a crash or a power loss mid-write. E1-AC2 then sets the torn file aside and the app starts with defaults, so the user's own reminders from E3 vanish from the app; SPEC Backups and restore rests on that one file | should fix | E1-AC8 writes to a temporary file and replaces settings.json in one step, tested under E1-AC10 |
| 11 | E3-AC2 says a saved change acts on the schedule at once, but the scheduler in SPEC Architecture takes no settings-change event and no E1 criterion covers one. Nothing says whether an edited «каждые N минут» reminder counts N from the save or from its last start, whether an «в заданное время» reminder moved to a later time today still fires today, or whether a reminder disabled or deleted while it repeats every 10 minutes for an answer (E1-AC7) stops and its notification goes. QA cannot judge E3-AC2, and E3 would have to reopen Core and its tests after E1 | should fix | E1-AC9 applies a saved change by the rule SPEC Architecture now states: an edited or new every-N reminder counts from the save, an edited at-time one takes its next due time from the new time and days (today if still ahead), a disabled or deleted one loses its repeats and its wait for an answer, the rest keep their state; tested under E1-AC10 |
| 12 | E1-AC3 says that after «Отложить» the reminder fires again in 10 minutes «а затем отсчёт снова N минут», which reads as the N-minute count starting when the snoozed reminder fires again. SPEC Architecture and E1-AC7 start that count only on «Закрыть» and keep it stopped while no answer comes, so a test written from E1-AC3 and one written from E1-AC7 expect different times for the same snoozed, then unanswered reminder | should fix | E1-AC3 now starts the N-minute count at the «Закрыть» of the snoozed repeat and defers to E1-AC7 while no answer comes, as SPEC Architecture says |
| 13 | E1-AC1 and E1-AC2 name the real file %APPDATA%\move-reminder\settings.json and E1-AC9 asks for a test of each, but nothing says the tests use another folder. The gate and its tests run on the owner's PC, before every commit and in local sessions, where from E2 on the owner uses the app every day; a test that removes the file to check a first start, or plants an unreadable one to check E1-AC2, resets the owner's reminders or leaves .bad files beside them | should fix | E1-AC10 has the core take the settings folder as a parameter and the tests work in a temporary folder, never %APPDATA%\move-reminder; SPEC Architecture and a CLAUDE.md boundary say the same |
| 14 | With autostart on from the first run (E2-AC7), the app runs in the tray whenever the user uninstalls it. E3-AC8 makes the installer close a running app, but no criterion asks the same of the uninstaller: E0-AC7 is checked on the hello world skeleton, and E2-AC7 and E2-AC10 only add registry keys to remove. Windows will not delete the exe of a running process, so the app keeps reminding after the uninstall and its files stay in %LOCALAPPDATA%\Programs\move-reminder | should fix | E3-AC9 has the uninstaller close the running app or ask to, and afterwards no process, installed file, shortcut, autostart key or AppUserModelID key remains, while %APPDATA%\move-reminder stays |
| 15 | The installer redistributes the .NET runtime, Windows Forms and WinRT.Runtime.dll under MIT, whose terms ask that the copyright and permission notice go with every copy, and Microsoft.Windows.SDK.NET.dll under Microsoft's distributable code terms. SPEC Dependency licences lists them, but no criterion has scripts/build or the installer put the project LICENSE and the third-party notices next to the app | should fix | E0-AC9 adds the MIT LICENSE to the repository and has the installer put it and THIRD-PARTY-NOTICES.txt with the licences of the shipped assemblies into the install folder, as SPEC Architecture (Установка) says |
| 16 | An autostart that is on is not kept across an update or a reinstall. A-5 asks that autostart survive installing the next version over the old one, and the scenario «Автозапуск» needs it on, but E3-AC8 checks only that an autostart the user turned off stays off. An update that runs the old uninstaller first, a usual NSIS way to drop files a new version no longer ships, deletes the HKCU Run key (E2-AC7), and the next start does not put it back because settings.json exists; a reinstall after an uninstall ends the same way, since the uninstaller removes the key and keeps settings.json (E0-AC7). The app then stops starting with Windows after an update, and no criterion or QA step would show it | should fix | open: E3-AC8 also checks that with autostart on, after the update and a reboot, the app starts by itself; and SPEC with a criterion says what the first run after a reinstall over kept settings does with autostart (for example: the choice to turn it off is kept in settings.json, and a run without that choice turns it on) |
| 17 | Until E3 the only way to change a reminder is to edit settings.json by hand (in E2 «Настройки» opens its folder, and E2-AC1 has QA lower the interval there), and the file stays editable afterwards, but E1-AC2 sets aside only a file that does not parse or has an unknown schemaVersion. Nothing says what the core does with a file that parses but holds a value the window refuses under E3-AC3: an interval of 0 or below, a time outside 00:00–23:59, no day chosen, an empty name, or two reminders with one id, on which E1-AC9 relies. An interval of 0 taken as is fires the reminder again right after every «Закрыть», and a value that throws on use can stop the app at every start, which autostart repeats at every login | should fix | open: E1-AC2 or a new E1 criterion, tested under E1-AC10: a file with a value outside the rules of E3-AC3 or a repeated id is set aside like an unreadable one, or the bad reminder is turned off, as SPEC Data model then says |
